# 评测集画像（Eval Set Profiling）设计文档

> 状态：**待评审**。本文档只做设计，不含实现代码。
> 关联功能：训练数据画像（`docs` 对应实现见 `backend/app/services/training_data/`、`frontend/src/pages/TrainingDataProfiles.tsx`）
>
> 需求原话：*「加一个评测集画像功能，支持任意的开源的评测集，方便用户针对性了解每一个评测集合的特性，评测集之间的问题」*

---

## 1. 目标与非目标

### 1.1 目标

1. **能装进任意开源评测集** —— 内置样例集开箱即用 + HuggingFace Hub 真实拉取，覆盖「任意」。
2. **看懂单个评测集** —— 不跑模型也能回答：这个集考什么、怎么考、有什么坑。
3. **看懂评测集之间的差异** —— 把多个集放在一起，回答「我该用哪个」「为什么两个集分数不能直接比」。

### 1.2 非目标

- 不做评测集「市场」的交易/评分排行（那是 `open_source_datasets` 的书签定位）。
- 不替代已有的评估执行链路（`Evaluation` / `EvalResult`）。画像只描述**数据本身**，不产出模型分数。
- 不做训练数据画像的重构。两者共用基础设施，但画像维度各自独立。

设计前对仓库的实测结论（决定了下面的方案选择）：

## 3. 核心设计决策

### 决策 1：`Dataset` 加判别字段，而非另建 `eval_sets` 表

**方案对比**

| | A. 并行 `eval_sets` 三表 | **B. `Dataset.dataset_kind` + 平行记录/画像表（采用）** |
|---|---|---|
| 能否直接被现有评估引擎消费 | ❌ 需桥接步骤再生成 `Dataset`+`QARecord` | ✅ 导入即写 `QARecord`，`POST /datasets/{id}/generate` 之外还可直接评估 |
| 数据源 | 双份真相（评测集存两处） | 单一真相 |
| 与仓库既有先例 | 仓库确实把 `qa_records` / `training_data_records` 分开 | 同构：实体唯一，记录层按形态分离 |
| 侵入性 | 低 | 中：`datasets.py` 列表查询加过滤 |

**采用 B。** 理由：画像的**唯一目的**是让人「针对性了解这个集」，进而**选它去评估**。若评测集是张孤岛表，用户画像完还得手工搬运一遍才能用，功能是断的。仓库对训练数据之所以能分表，是因为训练数据根本不参与评估；而评测集恰恰要参与。

**字段**：

```python
# backend/app/models/dataset.py
dataset_kind = Column(String(20), nullable=False, default="general", index=True)
#   general     —— 历史数据，无法判定用途（回填默认值）
#   training    —— 训练数据集（有 training_data_records）
#   evaluation  —— 评测集（有 eval_set_records）
```

回填策略：**存量行一律填 `general`，不猜**。猜错会让数据集从现有下拉框里消失，比信息缺失更糟。前端对 `general` 不做特殊展示。

### 决策 2：记录层与画像层用平行表 `eval_set_records` / `eval_set_profiles`

与 `training_data_records` / `training_data_profiles` 完全对称，但归一化列换成**评测集专属语义**（选项、答案类型、学科、难度……见 §5）。

`payload` JSONB 保留原始记录全文 —— 这是「支持任意开源评测集」的关键：未知字段永不丢失，且画像完成后仍可回溯。

### 决策 3：画像维度不复用 L1–L4

训练数据的 `suggest_level()`（`profiling.py:161-195`）依赖 `synthetic` 比例、`score_mean` 等**训练专属信号**，对评测集无意义。评测集用**题型 + 答案形态 + 学科覆盖**取代层级分级，见 §5。

> **`question_hash` vs `qa_hash` 是本设计最重要的一个细节。**
> 跨集比对**必须**用只含题干的 `question_hash` —— 同一个知识点在 C-Eval 与 CMMLU 里可能出现，但选项/答案不同。若用 `qa_hash` 比，重复率会被系统性低估。
> 反过来，`question_hash` 相同而答案不同，是一个**严重且真实存在的信号**，单独列为对比报告里的「答案冲突」项（§6.4）。

**题干归一化指纹算法**（`normalize.py`）：

```python
def _norm_for_hash(text: str) -> str:
    t = unicodedata.normalize("NFKC", text)      # 全角→半角，统一编码
    t = t.lower()
    t = re.sub(r"\s+", "", t)                   # 去所有空白
    t = re.sub(r"[^\w\u4e00-\u9fff]+", "", t)   # 去标点（ASCII + CJK）
    return t
# question_hash = sha1(_norm_for_hash(question)).hexdigest()
```

### 5.1 题型判定规则（确定性，无 LLM）

按优先级短路，命中即停：

```
1. 有 choices 且 answer_labels ⊆ choices     → mc
2. 有 answer_text 且 answer_text 可数值解析   → numeric
3. 有 target_chunk_ids / gold contexts       → retrieval
4. 含 tool/function 角色或多轮 messages      → agentic
5. 有 answer_text 且答案长度 > 20            → generate
6. 有 answer_text                            → judge
7. else                                     → other
```

### 5.2 质量分与问题清单

评分公式直接沿用 `profiling.py:238-253`（重复率 + 空值 + 过短 + 超长 + 自带分），保证训练/评测两套画像的「质量分」口径一致、可横向理解。

问题清单按阈值产出**中文短句**，前端每条渲染成一个 `Alert`：

| 阈值 | 问题文案 |
|------|----------|
| 答案位置分布偏离均匀 > 10% | `正确答案位置分布偏斜（C 占 38%），模型可从选项位置猜答案，分数会被高估` |
| 答案字面出现在题干 > 1% | `存在答案泄漏：{n} 题的正确答案字符串直接出现在题干中` |
| 正确项平均长度显著偏离干扰项 > 20% | `选项长度存在偏置：正确项平均 {x} 字，干扰项平均 {y} 字，可被长度启发式破解` |
| 题干内重复选项 > 1% | `{n} 题存在完全重复的选项，题目质量存疑` |
| 题干为空 | `存在空题干` |
| 答案位置分布均匀（无偏置） | `未发现明显结构性问题` |

## 6. 集间差异对比引擎 ★

这是用户明确要的**主功能**（「评测集之间的问题」）。

入口：`POST /api/v1/eval-set-profiles/compare`，body `{"profile_ids": ["...", "...", "..."]}`，支持 2–8 个集。

### 6.1 分布差异

对每个**共有维度**（题型、答案类型、学科、语言、难度、题干长度桶）逐维比较：

| 指标 | 公式 | 用途 |
|------|------|------|
| **总变差距离 TV** | `0.5 · Σᵢ \|pᵢ − qᵢ\|` | 主指标。直观，[0,1]，可直接说「这两个集的题型差了 62%」 |
| **Jensen–Shannon 距离** | `√(0.5·KL(P‖M) + 0.5·KL(Q‖M))`，`M=(P+Q)/2`，log₂ | 辅助。对长尾更平滑 |
| **余弦相似度** | 分布向量夹角 | 仅用于学科分布 |

对 N 个集输出 N×N 距离矩阵 + 每个维度一张分组柱状图。

### 6.2 学科覆盖重叠

```
Jaccard(A,B) = |S_A ∩ S_B| / |S_A ∪ S_B|
```

输出：
- 两两 Jaccard 矩阵；
- `only_in_a` / `only_in_b` 学科清单（C-Eval 有 52 科、CMMLU 有 67 科，差集直接告诉用户「补齐 XX 能力用另一个集」）；
- **覆盖热力图**：学科 × 集 的 0/1（可选按题量加权）矩阵。

### 6.3 格式兼容性判定

若两个集的 `primary_format` 不同，直接标红**「不可直接对比」**并说明原因：

> C-Eval 是选择题（4 选 1，要求 ExactMatch），GSM8K 是生成题（自由文本，需数值容差匹配）。两者的准确率不在同一量纲，横向对比无意义。

同时检查 `answer_type` 是否一致、`avg_prompt_tokens` 是否量级相近（差距 >3 倍会显著影响成本对比）。

### 6.4 交叉污染 / 答案冲突

跨集比对 `question_hash`：

```python
# 一次性取两个集的 (question_hash, qa_hash, answer_labels/answer_text)
dupes = hash_a ∩ hash_b
conflicts = [d for d in dupes if d.qa_hash_a != d.qa_hash_b]
```

输出：
- 重叠题数 / 重叠率；
- **答案冲突清单**（同题干、不同答案 —— 严重问题，说明至少一个集有错）；
- 冲突样例对照（前 N 条，题干并排展示）；
- 建议：若模型已在 A 上测过，B 与 A 重叠的题应从 B 中剔除后再测。

> 实现注意：跨集比对需要两个集都**已入库有记录**。若某集画像时触发了采样（`sampled=True`），污染检测结果标注为「基于样本，完整数据可能更多」。

### 6.5 选型建议

基于以上维度生成规则化建议（非 LLM，保证可复现）：

- 目标 = 中文多学科知识 → 提示选覆盖学科最多者，列出其独有学科；
- 目标 = 数学推理 → 优先 `numeric`/`generate` 题型集，给出与选择题集不可比的警告；
- 覆盖差异 < 20% 且题型一致 → 提示两者可互补使用以降低过拟合风险；
- 检测到答案冲突 → 提示先人工复核冲突题。


- **元数据**：`HfApi().dataset_info(repo_id)` → license / downloads / lastModified / cardData（取 `configs`、`language`、`task_categories`）。与 `open_source_datasets.py` 现有做法一致，避免重复实现 Hub 元数据抓取。
- **拉取策略**：优先 parquet（列存、`pyarrow` 只读所需列），大集用 `streaming=True` 但**统计阶段只读需要的列**并设置行数上限。
- **子集（config）**：C-Eval 52 个学科、MMLU 是 4 个 config，导入时让用户选「全量」还是指定 config/subset。

**任意性的实现：两段式映射**

```
第一段：EvalSetSpec 注册表（像 sync_adapters.py 的 SyncAdapterFactory.REGISTRY）
    已内置集的精确映射（列名 → 标准字段）
第二段：通用 auto-mapper（兜底，覆盖任意未知集）
    复用 datasets.py:474-489 已有的 KNOWN_KEYS 别名表，
    再叠加评测集专属别名：
      choices  ← options / choices / candidates / answers_options / distractors
      answer   ← answer / label / target / correct_answer / gold / answerKey
      subject  ← subject / discipline / category / topic / domain / field
      difficulty ← difficulty / level / grade / hardness
    命中不了的字段 → 全部塞进 payload，不丢
```

> 复用而非重写 `datasets.py` 的别名表是关键：上传路径与 HF 路径用**同一套**字段语义，避免两条入口产出的画像口径不一致。

## 8. API 设计

路由注册：`include_router(eval_set_profiles.router, prefix="/eval-set-profiles", tags=["Eval Set Profiles"])`

### ⚠️ 静态路由必须先于 `/{profile_id}`

Starlette 按**首个匹配**的路径正则分发，无类型兜底。`/samples`、`/hf/search`、`/compare` 若声明在 `/{profile_id}` 之后会被永久遮蔽、恒返回 422。

**这正是训练数据画像踩过的坑**，仓库已有回归测试 `backend/tests/test_route_order.py` 守着。本次必须补同名用例：

```python
@pytest.mark.parametrize("path", [
    "/api/v1/eval-set-profiles/samples",
    "/api/v1/eval-set-profiles/hf/search",
    "/api/v1/eval-set-profiles/compare",        # ← 最容易被遮蔽的一个
])
```

| Method | Path | 说明 |
|--------|------|------|

## 11. 风险与边界

| 风险 | 应对 |
|------|------|
| 静态路由被 `/{profile_id}` 遮蔽 | 声明顺序 + `test_route_order.py` 回归用例 |
| `ArrayType.contains()` 在 SQLite 下退化为子串匹配（`db_types.py:62-66` 已注明，`"llm"` 会误配 `"llm_x"`） | 测试数据用整词取值；标签过滤只在 PG 下测 |
| 全量 C-Eval/CMMLU 数据量大 | 沿用既有上限：`MAX_TRAINING_RECORDS=50000`、`MAX_PROFILE_ROWS=200000`、`SYNC_PROFILE_LIMIT=20000` |
| HF 网络不可达 / 仓库改名 | 加载失败给出明确中文错误并保留 `source_meta`；内置样例保证离线仍可用 |
| 长任务进度丢失 | 每个阶段 commit 进度（沿用 `profile_runner` 的 10/50/80/85/95/100） |
| 画像 JSON 过大 | 学科分布 top 50、样本预览 5 条、字段画像 40 字段（沿用既有截断常量） |
| 污染检测误报 | 短题干（<10 字）指纹易撞 → 低于阈值不计入重叠率，并在报告中标注阈值 |
